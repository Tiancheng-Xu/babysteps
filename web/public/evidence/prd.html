2. 一句话定义与产品背景

一句话：先让家庭用三分钟亲子任务获得轻量陪伴体验，再按需进入登录、成长积分、任务购买和链上证书等进阶能力。

产品假设是：日常陪伴重复、反馈弱，家长需要容易开始和能看见积累的体验；钱包和测试网会提高第一次使用门槛，因此目前首页采用访客优先。没有可查证用户访谈、真实转化率或育儿效果评估，不能把这个假设讲成经大规模市场验证的结论。

演进分为三层。早期 OnchainNotebook 用非 ERC-20 成长星记录喂养、散步、共读、赠送和公开便签；成长市集增加 ERC-20 BabyCoin、Provider 审核、Chainlink 随机任务、购买与不可转让证书；PR #83 所在版本把访客任务放到首页主路径，并公开中文产品说明和流程录屏。中国、日本、城市选项只是演示中的粗粒度本地选择，不代表当地活动、社交关系或推荐后台已经落地。

6. 端到端正常、失败与恢复流程

访客主流程：

选择阶段 / 市场 / 粗粒度城市
  → 按阶段得到固定任务 → 开始 → 标记完成
  → 当前浏览器本地保存 → 刷新恢复
  → 按需进入个人中心或进阶 Web3

任务市集流程：

Provider 建草稿与 metadata hash → requestTask
  → PendingReview → Owner approveTask
  → PendingRandomness → VRF 回调 → Active / 固定价格与窗口
  → 家长网络就绪、余额与资格校验 → exact approve → 成功回执
  → buy → 成功回执 → Worker 验购买 → 解锁内容与评论
  → 家长提交完成说明及 hash → 受限钱包确认完成
  → GrowthCertificateSBT 按 purchaseId 铸一张证书 → 回读

失败与恢复：用户拒签时不增加成长值、不标记已购；网络不正确时提供切网；读取权限或购买事实失败时关闭敏感操作，RPC 不可用返回 503，不猜测用户没买。任务被拒绝、暂停或已过期时不能购买。approve 成功而 buy 没成功时，应按现有 allowance / purchase 状态重新核对，不把两步当一个不可分的操作。

兑换后若 Router allowance 大于 0，当前 Hook 锁定下一次报价与输入，引导用户单独签名清零；链上读回为 0 才解除 Gate。纪念卡随机请求超时可按规则 recover 退款 / 解锁；迟到随机回调不能再结算已恢复请求。

访客存储不可用时体验仍可继续，但不能保证刷新保留。损坏或不符合 v1 枚举的记录被当作无有效状态；本轮没有注入异常重跑测试。登录后的跨设备迁移、家庭长期档案不能从一个 CTA 推导为已实现。

8. 状态机、业务规则、幂等与未知结果

任务合约实际枚举：None → PendingReview → PendingRandomness → Active，审核拒绝进入 Rejected。paused 是独立布尔值；是否过期由 block.timestamp >= closesAt 决定。不要把设计稿中的 Draft、Expired、Paused、RandomnessFailed 全部说成 V2 合约枚举。链下草稿是另一个实体。

成长规则：成长值阶段 <3 星蛋、3–7 星芽、8–14 探索星宝、≥15 闪耀星宝。成长奖励增加累计成长值与可用余额；赠送、兑换、购入、测试分配、Provider 收款不能伪造成本人活动成长。喂养冷却 3–4 小时 / 每日 6 次，散步 8–12 小时 / 每日 2 次，共读 4–6 小时 / 每日 3 次；按 UTC+8 日编号。虚拟伙伴冷却不代表真实婴儿需求，不用精确倒计时制造照护压力。

购买：任务 Active、未暂停、未过期、钱包未购过才允许 buy。合约用 msg.sender 得买方，用 SafeERC20.safeTransferFrom 扣精确锁价，交易失败整体回滚。purchaseIdForBuyer[taskId][wallet] 抑制重复购买。广播哈希不代表成功；回执与链上读回决定下一步。

完成：D1 的 completion_submissions.purchase_id 唯一，完全相同的 evidence hash、wallet、URI 返回已有记录；不同内容冲突返回 409。合约确认受 COMPLETION_RELAYER_ROLE 约束；相同已完成 evidence hash 走已有证书，不同 hash 拒绝。证书层再核对 recipient / URI，防止同 purchaseId 改成另一张证书。当前 D1 唯一键只使用 purchaseId；若将来同时服务多个 Marketplace，需要把合约身份纳入键，不能未经改造直接宣称跨合约幂等安全。

纪念卡：抽卡成本 12 个 OnchainNotebook 成长星，不能说成任意 BABY 余额都可支付。四阶段 / 四稀有度，稀有度概率 70/22/7/1；三张同系列同稀有度可融合，成功概率按级别 100/70/40%，失败随机烧一张、解锁两张，最高级别不能继续融合。请求 24 小时超时后可以 recover，退款或解锁，迟到回调忽略。真实抽卡已取证，真实融合仍需自然获得三张匹配卡。

未知结果：链上操作超时并不证明失败。先根据哈希、receipt、purchaseId、余额 / allowance 读取确认，避免重新创建同一笔业务。当前项目有查询和幂等基础，但没有证据说明已实现跨刷新持久化的通用交易恢复账本；项目讲述不要把其他 Agent 项目的操作账本搬过来。

11. 架构与技术取舍

Pages Edge SSR 公共摘要 → React 水合 → 客户端激活 Privy / wagmi
                                      ├─ viem → Sepolia 合约 / VRF / Uniswap
                                      └─ 业务 Worker → D1 元数据 / 会话 / 评论
合约事件 → The Graph → 可检索历史视图
浏览器性能白名单 → Worker → 临时 AWS 队列 / Cleaner → PostgreSQL 聚合
  1. 先体验再钱包。 访客任务用固定阶段规则和 localStorage；替代是强制钱包登录或先建家庭云档案。前者使体验更容易开始，代价是不能同步、不能证明真实活动。代码实际 guestTaskFor(stage) 只按阶段选任务，market / city 不参与个性化算法；不要说“AI 匹配中日同城活动”。
  2. 链上权利与链下内容分开。 合约保存价格、购买、角色、完成 hash，D1 保存视频链接、文字与会话。替代是全部内容上链；目前组合降低写入成本和隐私暴露，但依赖 Worker / 链下内容可用性，metadata hash 只证明内容一致，不证明内容真实。
  3. SSR（Server-Side Rendering，服务端渲染）与私有激活分开。 Cloudflare 输出可读公共壳；钱包、Privy、余额、会话客户端挂载。替代为纯 CSR（Client-Side Rendering，客户端渲染）或所有用户数据 SSR。当前选择保证公共页面可读并减少私有数据进入共享 HTML / 缓存；不等于已实现 SSG 或岛屿架构。
  4. 精确 allowance 代替无限授权。 额度读回、approve、buy / swap 分阶段确认。多了一笔交易或残余清零，但便于解释余额和权限暴露。登录签名不能代替 ERC-20 approve，approve 也不是实际付款。
  5. VRF 与完成审查职责分开。 VRF（Verifiable Random Function，可验证随机函数）只提供可核验随机价格 / 窗口 / 卡片结果。替代是服务端随机数；VRF 可核对，但需要订阅余额和异步等待。它不能判断现实陪伴是否完成，完成目前是受限角色的批准事实。
  6. 任务证书不可转让。 V2 用 ERC-721 + ERC-5192 SBT（Soulbound Token，绑定凭证）；替代是可交易 NFT。当前让完成证明和买方绑定；它也不是实名或真实成长证明，不能保证换钱包后继承。
  7. 性能链路按受控运行取证。 SQS 解耦、一次性 ECS Cleaner 清洗、UUID 去重、小时聚合；替代是直接同步写数据库或常驻服务。设计能展示可靠接收与清洗，代价是较多组件与成本管理；当前无需把临时管线长期运行来维持作品站。

13. 非功能要求、安全、性能、成本与降级

身份安全。 Worker 不接收私钥 / 助记词；challenge nonce 一次使用且有时限；会话 Cookie 为 HttpOnly、Secure、SameSite=Lax，服务器保存 token hash。CORS 允许配置来源、凭据与必要方法；它不能代替业务鉴权。API session、Provider / Owner / Relayer 角色、链上已购事实分别校验。

隐私。 RenderState 只白名单 mode/pathname/version，安全序列化转义 < > & 与 Unicode 行分隔符；不能把地址、会话、余额或儿童资料注入初始化状态。client-shell、含 query / Authorization / Cookie、404 请求使用 private,no-store。事件日志只输出受限元数据，证据不写 Token、Cookie、完整签名或儿童输入。

渲染。 Pages 默认 2500 ms 硬超时；失败输出 CSR 静态文档。客户端只有 state.mode=ssr、路径和构建版本匹配、DOM marker=ssr、根有子节点才 hydrateRoot。可恢复水合错误记录 hydration.recoverable_error；未捕获错误或同步异常最多一次卸载、清空根、createRoot 重挂载并记录 csr.fallback。这不是把所有告警都当致命故障。

可访问性与响应式。 产品希望大文字、大按钮、键盘焦点、状态文字和 reduced-motion；访客版验收要求 375 / 390 / 430 / 1440 无根级横向溢出，主要触控目标至少 44px。旧版目标含 320px 与 48px；本轮未重新审全站 WCAG，不宣称全部达到 AA。

性能口径。 2026-08-31 受控运行 LCP n=6、P75=2568ms，CLS n=9、P75=0.090，INP n=4、P75=48ms。LCP 受控值仍有改进空间，样本小且运行条件特定；FCP / TTFB 是诊断指标。TLS 不可分时标 unavailable；执行但健康零错误、没有样本、功能未执行必须区分。不要宣称线上用户性能优化了某个百分比。

成本 / 运行。 8月31日性能取证后项目 schema / Stack 与所列临时资源已清理。9月23日 17 区域清单 stoppableRunningResources=0，仍保留共享受保护 RDS，状态为 inaccessible-encryption-credentials，不是“已停止且零费用”；S3 等也不能用 stop 等价处理。该清单是历史快照，本轮未做 AWS 操作，不能说当前账号全部停机、删除或免费。

第 2 分钟：走完整链路。 “Provider 先存 D1 草稿和 canonical metadata hash，再请求链上审核。Owner 批准后异步等 VRF，激活任务并锁定所有家长共用的价格和窗口。买方按精确额度 approve 后 buy，合约从 msg.sender 取身份，付款到 Provider payee。后端核对已购买才解锁内容。完成说明与 hash 幂等存 D1，受限角色确认后按 purchaseId 铸 SBT。VRF 证明随机数，不证明现实活动真实。”

第 3 分钟：两个技术难点。 “一是身份状态不能混为一谈。Privy 登录、Worker 会话、钱包账户、Sepolia 网络、Provider / Relayer 权限、ERC-20 allowance 和 receipt 都是独立事实。用户连了钱包不一定有角色；授权成功也还没付款。二是首屏和交互不能互相污染。Cloudflare SSR 输出安全公共壳，初始化只带 mode/path/version，浏览器先严格判断才 hydrate。之后才挂钱包 SDK；可恢复错误计数，致命错误才一次重挂载，避免无限恢复循环。”

第 4 分钟：取舍与失败。 “链上存权利和 hash，链下存内容，省成本也给内容和隐私留调整空间，但服务可用性仍依赖链下。精确授权比无限授权麻烦，换来小的授权面和可验证收尾。SBT 不可转让，使证书绑定购买者，但不解决实名真实性。签名被拒绝不能乐观加积分；RPC 故障不能推断未购买；交易超时先查回执与业务状态再重试。纪念卡超时可以退款 / 解锁，迟到回调不能重复结算。”

第 5 分钟：验证与诚实边界。 “真实回执证明 Sepolia 任务审核、购买、临时授权完成、SBT #1 和撤权；Graph 读回两任务两购买一证书。抽卡也有真实 #1，但融合仍缺匹配卡和真实交易。最新已查历史发布是 PR83，部署和品牌域名 bundle 一致，深链200、未知404、附件可读。8月31日性能是 232 事件的受控窗口，LCP 只有6个样本，P75 2568ms不能吹成优秀生产表现。临时 AWS Runtime已清理，长期 Relayer和新版30项全流程还要补验。我的价值是把每一步的权限、状态和验收对象讲清，并按本人参与事实说明怎么落地。”

18. 追问树与大白话复习

每个回答按“机制 → 为什么 → 失败怎么办 → 哪份证据 → 我做了什么”展开；最后一句必须由本人补全。

  1. 为什么钱包连上还买不了？ 钱包连接是知道账户，chainId 判断网络，余额 / allowance 判断资产授权，合约状态与角色判断业务资格；买入还要签名和 receipt。追问：切账户后会话钱包如何重新证明？不能沿用旧账户资格；现场查 identity Hook，不说未经验证的自动恢复。
  2. approve 与 buy 区别？ approve 是允许合约最多花多少；buy 才实际转款和写购买。大白话：先给“扣款额度”，再下单。追问中间失败：查 allowance / purchaseId，不能重复买；余额和付款不能只信前端。
  3. hash 与 receipt 为什么分开？ hash 是已广播的查询单号；receipt 成功才是执行结果。追问超时：未知不是失败，先查再决定；当前没有通用持久化交易账本，不借用别的项目概念。
  4. 为什么同时用链和 D1？ 链保存权利、状态和 metadata hash，D1保存文本与视频链接；用 taskKey 绑定。追问 DB有人改内容：重新算 hash与合约比对；hash证明一致不是证明真实。
  5. Privy 登录等于业务授权吗？ 不等于。第三方身份入口、challenge钱包签名、HttpOnly应用会话、链上角色是四层。追问重放：5分钟challenge、精确message、recover地址、原子consume；冲突409。Cookie安全与CORS分别解决不同问题。
  6. SSR 和水合怎么配合？ 服务端先给能看的公共壳，浏览器接管同一结构。追问为什么版本 / 路径 / marker / DOM都检查：防止旧HTML、错页面或空壳被当成当前SSR；钱包SDK后激活，私有状态不灌HTML。
  7. 所有水合错误都回退吗？ recoverable只记录；uncaught / 同步异常一次CSR。大白话：小偏差记账，真正接管失败才换一套渲染。追问恢复风暴：recovered布尔锁+microtask，最多一次；源代码E12。
  8. 随机性与真实性区别？ VRF让价格和卡片结果可核验，不能判断家长真的完成陪伴。追问“自动Oracle”在哪：历史完成是临时Relayer签名且已撤权；不要说KMS生产自动服务已上线。
  9. 怎么保证不重复发证？ D1 purchaseId唯一、相同hash重放返回原记录；合约完成hash冲突拒绝；SBT purchaseId→tokenId再次校验owner/URI。追问多合约：当前D1要扩键，不能直接横向复用。
  10. SBT和普通NFT差别？ SBT这里禁止转让 / approval，是绑定完成记录；不是证明实名或真实成长。追问钱包丢失：目前没有已确认恢复产品，不能承诺自动迁移。
  11. 历史性能是不是线上RUM？ RUM（Real User Monitoring，真实用户监控）要来自真实生产用户；此处是受控浏览器、临时AWS窗口。追问统计：样本数必须一起说，LCP n=6；没样本、不可用、健康零事件分别解释。不能用截图证明常驻服务。
  12. 为什么没有真融合也说实现？ 实现是源码与本地测试层；真实链上验收还缺三张自然匹配卡。给抽卡回执、明确融合partial，避免把管理员造卡当业务证据。

记忆串：先体验 → 再身份 → 链上资格 → 精确额度 → 签名 / 回执 → 内容与凭证 → 证据分层。
